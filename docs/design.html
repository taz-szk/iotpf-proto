Requirements Specification

IoT プラットフォーム 要件定義書

版: 1.0 対象: マルチテナント型 IoT デバイス管理基盤
01

目的・背景

複数の企業（テナント）が同一インフラ上で自社 IoT デバイスのテレメトリ収集・監視・管理を行えるマルチテナント型プラットフォームを構築する。各テナントのデータは論理的・物理的に分離され、テナント管理者が独自にデバイス・ユーザー・アラートを管理できる。

02

ステークホルダー・ロール

ロール区分主な権限
プラットフォーム管理者Platformテナント CRUD、ファームウェア管理、OTA 配信、全テナント統計閲覧
テナント管理者Tenant / adminデバイス・ユーザー・アラートルールの管理、OTA 配信（自テナント）
テナントオペレーターTenant / operatorデバイス操作、OTA 配信（自テナント）、センサーデータ閲覧
テナントビューアTenant / viewerダッシュボード閲覧のみ
IoT デバイスDeviceMQTT 経由テレメトリ送信、OTA コマンド受信（mTLS 認証）
03

機能要件

FR-01 テナント管理
マルチテナント自動プロビジョニング
テナント作成時に PostgreSQL スキーマ・InfluxDB org・Grafana org を自動作成。ステータス: active / suspended / deleted。
FR-02 ユーザー管理
プラットフォーム／テナントユーザー認証
email + bcrypt パスワード認証。JWT アクセストークン (15分) + リフレッシュトークン (30日)。パスワード変更機能付き。
FR-03 デバイスプロビジョニング
ブートストラップトークンと mTLS 証明書発行
一時ブートストラップトークンで認証後、Step-CA が mTLS クライアント証明書を自動発行。デバイス上限数・有効期限を設定可能。
FR-04 テレメトリ収集
MQTT → InfluxDB パイプライン
EMQX Webhook → Ingestion Service → InfluxDB 2.x。センサーキーは動的（固定スキーマなし）。テナントごとに InfluxDB org で分離。
FR-05 接続状態管理
デバイス online / offline 記録
EMQX の接続・切断イベントを Webhook で受信し、PostgreSQL とInfluxDB に時系列ステータスを記録。
FR-06 アラート管理
ルールベース通知
条件: above / below / equal / device_offline。トリガーモード: consecutive / duration。重要度: info / warning / critical。メール通知。
FR-07 OTA ファームウェア更新
署名付き URL によるセキュアな配信
最大 100MB のファームウェアを MinIO に格納。署名付き JWT トークン（24時間有効、UUID/UUID 形式検証）でダウンロード。
FR-08 ダッシュボード
Grafana SSO 統合
Auth Proxy による SSO。テナントごとに Grafana org を分離。テレメトリ・デバイス稼働率を可視化。
FR-09 プロビジョニングトークン
テナント発行トークン管理
テナントごとに複数トークンを発行。最大デバイス台数・有効期限の設定。登録済みデバイス数を追跡。
FR-10 公開アクセス
認証なしデータ閲覧
テナントが発行する public_token で、特定テナントのセンサーデータを認証なしで閲覧可能な API を提供。

05

制約条件

  • デプロイ環境: Linux サーバー + Docker Compose（単一ホスト構成）
  • MQTT ブローカー: EMQX 5.x（ACL は設定ファイルおよびデータベース認証で管理）
  • 時系列データベース: InfluxDB 2.x（Flux クエリ言語を使用）
  • PKI: smallstep/step-ca による自己署名 CA（外部 CA への依存なし）
  • MailHog を SMTP 中継として使用（本番では外部 SMTP に切り替え可能）
  • インメモリのレート制限・JTI ブロックリストはプロセス再起動でリセットされる（単一プロセス前提）

データストア設計方針

PostgreSQL — メタデータ・テナントデータ

  • public スキーマにプラットフォーム共通テーブル（tenants, platform_users, provisioning_tokens）
  • テナントごとに tenant_{uuid} スキーマを動的作成（CREATE SCHEMA IF NOT EXISTS）
  • スキーマ変更は ALTER TABLE ... ADD COLUMN IF NOT EXISTS で無停止マイグレーション

InfluxDB 2.x — 時系列データ

  • テナントごとに org を分離し、テナント専用トークンで読み書き（最小権限）
  • バケット: telemetry（センサーデータ）、接続状態は measurement device_status
  • Flux クエリを使用。センサーキーは固定スキーマなし（動的フィールド）

MinIO — ファームウェア

  • バケット firmware に {tenant_id}/{firmware_id} キーで保存
  • ダウンロードは署名付き JWT トークン経由（直接公開しない）

セキュリティ実装詳細

機能実装クラス／ファイル詳細
レート制限app/services/rate_limiter.pyIP をキーとする失敗カウント辞書。threading.Lock でスレッドセーフ。WINDOW_SEC=900、MAX_FAILURES=5。TTL 超過エントリは次回アクセス時に自動削除。
JTI ブロックリストapp/services/token_blocklist.pyJTI → 失効 monotonic 時刻 の辞書。is_revoked() / revoke_jti(jti, ttl_sec)。ログアウト・トークンローテーション時に登録。
token_versionplatform_users.token_versionパスワード変更で +1。/auth/refresh 時に DB と照合し、不一致なら 401。全リフレッシュトークンを一括無効化できる。
minio_key 検証app/services/minio_client.py_MINIO_KEY_RE = ^UUID/UUID$ で正規表現検証。JWT 内の minio_key がこの形式でなければ ValueError を送出。
EMQX Webhook 認証app/routers/emqx_events.pyリクエストヘッダの X-Webhook-Secret を settings.emqx_webhook_secret と比較。不一致で 403。
タイミング均等化app/routers/tenant_auth.pyテナント不存在・ユーザー不存在の早期リターン経路でも bcrypt 相当の時間を消費（_equalize_timing()）。列挙攻撃を防ぐ。
Grafana SSO 保護docker-compose.yml, nginxAuth Proxy を grafana-net (172.30.0.0/24) に限定。GF_AUTH_PROXY_WHITELIST で設定。
UUID/firmware_id 検証app/routers/firmware.py_validate_uuid() で [0-9a-f]{8}-… の正規表現検証。SQLi・パストラバーサルを防ぐ。

単体試験観点

AUTH 認証サービス

UT-AUTH-01
JWT アクセストークンの生成・検証が正常に機能すること
期待: デコード後に sub・type・exp クレームが含まれる
必須
UT-AUTH-02
リフレッシュトークンに jti クレームが含まれ、発行毎にユニークであること
期待: 同一ペイロードで2回発行した jti が異なる UUID
必須
UT-AUTH-03
無効・期限切れトークンに対して verify_token が None を返すこと
期待: 改ざんトークン・期限切れトークンで None
必須

RATE レート制限

UT-RATE-01
MAX_FAILURES 回の失敗後に is_rate_limited が True を返すこと
期待: 5 回 record_failure 後に is_rate_limited("key") == True
必須
UT-RATE-02
WINDOW_SEC 経過後に古いエントリが削除されること
期待: past 時刻のエントリは is_rate_limited で無視される
必須
UT-RATE-03
clear_failures 後にカウンターがリセットされること
期待: 5 回失敗後 clear_failures → is_rate_limited == False
必須
UT-RATE-04
異なる IP のカウンターが独立していること
期待: IP-A がブロックされても IP-B は is_rate_limited == False
必須

TOKEN トークン失効

UT-TOKEN-01
revoke_jti した JTI が is_revoked で True を返すこと
期待: revoke_jti("jti", 3600) → is_revoked("jti") == True
必須
UT-TOKEN-02
TTL 経過後に revoked エントリが自動削除されること
期待: ttl=0.001 で revoke 後 sleep → is_revoked == False
必須

MINIO minio_key バリデーション

UT-MINIO-01
正規の UUID/UUID 形式の minio_key でトークンが正常デコードできること
期待: payload["minio_key"] == 発行時の値
必須
UT-MINIO-02
../../etc/passwd 形式の minio_key を含むトークンが ValueError を送出すること
期待: decode_firmware_download_token → ValueError("minio_key")
必須

SEC 認証・レート制限

SEC-01
ログインを 5 回連続で失敗すると次のリクエストが 429 になること
期待: 6 回目の POST /auth/login → 429 Too Many Requests
必須
SEC-02
ログイン成功後にカウンターがリセットされ、再度失敗カウントが開始されること
期待: 成功後の失敗は 401（429 ではない）
必須
SEC-03
ログアウト後にリフレッシュトークンが無効化されること（JTI 失効）
期待: POST /auth/logout 後に同トークンで POST /auth/refresh → 401
必須
SEC-04
トークンローテーション: 一度使用したリフレッシュトークンが再使用不可になること
期待: /auth/refresh 成功後、同トークンで再度 /auth/refresh → 401
必須
SEC-05
パスワード変更後に旧リフレッシュトークンが無効になること（token_version）
期待: /auth/change-password 後に旧 refresh_token で /auth/refresh → 401
必須

SEC インジェクション・パストラバーサル

SEC-06
minio_key に ../../etc/passwd を含む JWT でダウンロードが拒否されること
期待: GET /firmware-download?token=… → 403
必須
SEC-07
UUID 形式でない firmware_id でリクエストが 422 になること
期待: firmware_id="../../etc" → 422 Unprocessable Entity
必須
SEC-08
EMQX Webhook への不正シークレットリクエストが 403 になること
期待: X-Webhook-Secret ヘッダ不一致 → 403
必須

SEC テナント分離

SEC-09
テナント A の JWT でテナント B のデバイス情報にアクセスできないこと
期待: 403 または 404
必須
SEC-10
Grafana の Auth Proxy が grafana-net 以外のサブネットからの X-WEBAUTH-USER を無視すること
期待: 外部からの直接 Grafana アクセスで 401 / ログインページにリダイレクト
必須
SEC-11
viewer ロールのテナントユーザーが OTA 配信を実行できないこと
期待: viewer トークンで POST /me/devices/{id}/ota → 403
必須

02

トークンリフレッシュ / JTI ローテーションフロー

POST /auth/refresh — JTI ブロックリストと token_version の二重検証を行い、使用済み JTI を即座に失効させる。

sequenceDiagram
    participant C as Client
    participant A as core-api
/auth/refresh
    participant BL as token_blocklist
    participant DB as PostgreSQL

    C->>A: POST /auth/refresh {refresh_token}
    A->>A: verify_token(refresh_token)
    alt 署名不正 or 期限切れ or type != refresh
        A-->>C: 401 Invalid refresh token
    else 有効
        A->>BL: is_revoked(jti)
        alt 失効済み
            BL-->>A: true
            A-->>C: 401 Token has been revoked
        else 有効
            BL-->>A: false
            A->>DB: SELECT user WHERE id = sub
            alt ユーザー不在 or 非アクティブ
                DB-->>A: null / inactive
                A-->>C: 401 Invalid refresh token
            else tok_ver 不一致
                A->>A: payload.tok_ver != user.token_version
                A-->>C: 401 Token has been revoked
            else 全検証通過
                A->>BL: revoke_jti(old_jti, remaining_ttl)
                A->>A: 新 jti で access_token + refresh_token 生成
                A-->>C: 200 {access_token, refresh_token}
            end
        end
    end

Security Feature Design

TOTP 二要素認証 設計書

版: 1.0実装: v1.0.2参照: docs/superpowers/specs/2026-08-31-totp-mfa-design.md
01

概要・設計方針

partial_token アプローチ: ログイン成功後、MFA が必要な場合は通常の access_token の代わりに partial_token（有効期限 10分）を発行する。TOTP 検証成功後に正式な access_token + refresh_token を発行する二段階フローを採用。

対象ユーザー

  • プラットフォーム管理者 — /auth/totp/* エンドポイント群
  • テナントユーザー — /tenant-auth/totp/* エンドポイント群（対称設計）

グローバル制御

プラットフォーム管理者が PATCH /platform/mfa-settings で platform_required / tenant_required を ON/OFF できる。各フィールドは独立して制御可能。

02

Alert Service Design

アラートメール 送信トリガー仕様

版: 1.0参照: alert-service/app/scheduler.py · notifier.py · evaluator.py評価間隔: 60秒
01

動作概要

APScheduler が 60秒間隔（EVAL_INTERVAL_SEC）で全テナントのアクティブなアラートルールを評価する。メール送信は「状態変化」にのみ反応する設計で、条件が継続して満たされても送信は繰り返されない。

02

連続条件時のメール送信挙動

1回だけ送信（状態変化検知型）。 条件が満たされ続けても追加メールは送られない。条件が解消されたときに [RESOLVED] メールが1通送信される。

評価ループの核心ロジック（scheduler.py:43）

条件動作
should_alert == True かつ 未解消イベントなしalert_events に INSERT → メール送信（アラート）
should_alert == False かつ 未解消イベントありalert_events を解消 → メール送信（[RESOLVED]）
上記以外（条件継続中 / 正常継続中）何もしない（サイレント）

イベント管理は alert_events テーブル（resolved_at IS NULL = 未解消）。既存の未解消イベントがある間は新規メールを送らない。

時系列での挙動（60秒ごとの評価）

経過時間状態メール
t=0正常—
t=60s条件一致（初回）📧 アラート送信
t=120s条件継続サイレント
t=180s条件継続サイレント
t=240s条件解消📧 [RESOLVED] 送信
t=300s正常—
03

送信トリガー

トリガー件名プレフィックス発火条件
テレメトリアラート発火[SEVERITY]InfluxDB テレメトリが閾値条件を満たし、かつ同ルールの未解消イベントが存在しない
アラート解消[RESOLVED]発火中アラートが閾値条件を満たさなくなった
デバイスオフライン[SEVERITY]last_seen_at が DEVICE_OFFLINE_THRESHOLD_SEC 超過、かつステータスが offline でない。送信後に devices テーブルを offline マークするため再接続まで再送なし
04

テレメトリ評価のトリガーモード

trigger_mode発火条件使用パラメータ
consecutive最新 N サンプルが連続して閾値条件を満たすconsecutive_count
duration過去 D 分のサンプルがすべて閾値条件を満たすduration_sec
consecutive_and_duration連続カウント AND 継続時間の両方を満たすconsecutive_count + duration_sec

InfluxDB クエリ範囲: max(duration_sec + 60, consecutive_count × 60 + 60) 秒。データ取得できない場合は should_alert = False（誤報なし）。
