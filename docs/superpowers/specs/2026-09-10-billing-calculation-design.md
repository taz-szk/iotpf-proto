# 料金積算機能 設計仕様書

## 概要・目的

対象月の基本料金と、システムから取得した統計情報（従量課金対象）ごとの利用量に単価を乗じた金額を合算し、月額請求金額を算出・確定するプロセスを定義する。

**背景:** [[project_tenant_billing_future]] — テナント統計機能（総デバイス数・データポイント数・アラート件数・プロビジョニング可能数等）の実装を土台に、これらを課金根拠とする料金積算機能を構築する。

**スコープ外（今回定義しない）:** 請求書ドキュメント（PDF等）の生成・送付、実際の決済処理。本仕様は「いくら請求すべきか」を確定するところまでを対象とする。

---

## 1. 積算ロジック

```
月額請求総額 = 基本料金 + Σ(各従量項目の利用量 × 単価) + 消費税
```

### 課金項目と定義

| 項目 | 定義 | 備考 |
|---|---|---|
| 基本料金 | 契約ごとに毎月固定で発生する料金 | テナント／契約プランごとにマスタ設定 |
| 当月データポイント数 | 当月1日00:00:00〜末日23:59:59（JST）にプラットフォームで処理・保存されたテレメトリ総数 | 既存の`data_points_this_month`と同じ集計元（InfluxDB） |
| 当月デバイス数 | **月内に1度でも通信したユニークデバイス数**（ユニークdevice_id数） | 月末スナップショット方式は採用しない（後述「決定事項」参照） |
| プロビジョニング可能数 | 有効かつ未失効のブートストラップトークンの残り登録可能数の合計 | **無制限トークンを持つテナントは本項目の従量課金対象外**（後述） |
| アラートイベント数 | 当月内に発報されたアラート総数 | 既存の`alert_events_this_month`と同じ集計元 |

## 2. 決定事項（前回のブレストで確定）

### 2.1 当月デバイス数の定義
「月末スナップショット」ではなく「月内ユニーク通信デバイス数」を採用。理由:
- 月末スナップショット方式は、月末直前の解約・削除で課金を回避できる歪んだインセンティブを生む
- 既存のInfluxDBテレメトリデータ（`data_points_this_month`と同一データソース）から`device_id`のユニーク数を取得できるため、新規の追跡機構が不要

### 2.2 無制限プロビジョニングトークンの扱い
**無制限（`max_devices: null`）トークンは、PF管理者のみが発行可能な「隠し仕様」とする。** テナント管理者は発行不可。

**要実装（現状の差分）:** 現在 `core-api/app/routers/tenant_portal.py` の `POST /me/tokens` は `max_devices: null` を受け付けて無制限トークンを発行できてしまう（`core-api/app/routers/provisioning_tokens.py` のPF管理者向けエンドポイントと同じ挙動）。これを塞ぎ、テナントポータル側は `max_devices` に有限値（`gt=0`）を必須とするようバリデーションを追加する必要がある。

**課金上の扱い:** 無制限トークンを持つテナントは、「プロビジョニング可能数」の従量課金対象から除外する（個別契約・固定料金等でPF側が別途取り決める前提とし、本バッチ処理は無制限テナントをスキップまたは固定金額行として扱う）。

### 2.3 月末データの遅延到着
タイムスタンプ（発生日時）ベースで集計するが、**締め切りルールを設ける**：集計バッチは対象月の翌月X日X時（例: 3日0時JST、具体的な日数は運用開始前に確定）に実行し、それ以降に遅延到着したデータは**切り捨てずに翌月分としてカウントする**（実際に発生した利用を消さない方を優先）。締め切りを過ぎた後の遡及訂正は「手動リカバリ機能」（4.2節）でカバーする例外処理と位置づける。

### 2.4 単価変更のタイミング
**単価変更は必ず翌月から適用**とする運用ポリシーを採用し、月内での即時適用・日割り計算は行わない。マスタの「適用開始日」フィールドは「未来の変更を予約する」用途として残すが、UIは当月中の日付を適用開始日として設定不可とするバリデーションを入れる。これにより月内レート切替の複雑さを設計上排除する。

### 2.5 ビルショック対策
**ハードキャップ（自動遮断）は採用しない**（テレメトリ欠損という別の障害を誘発するため）。代わりに以下の2層で対策する:

1. **プラットフォーム層（根本対策）:** MQTTブローカー（EMQX）のper-client rate limitingで、暴走デバイスからの異常な流入そのものを抑制する。課金ロジックより先に効く一次防衛線。
2. **課金/監視層（可視化）:**
   - テナントごとに「想定利用量」をマスタに持たせ、当月累積が閾値（例: 150%）を超えたらPF管理者・テナント管理者へ通知（監査ログ記録＋メール送信）。実際の対処（レート制限強化・個別デバイス無効化等）は人間が判断して実施する。
   - 個別デバイス単位の異常検知（直近1時間のデータ送信/アラート発報レートが、その デバイスの過去平均のN倍を超えた場合にフラグ）を別途検討する。集計後の合算値だけでは暴走デバイスを特定できないため。

## 3. マスタ設定（単価管理機能）

- 基本料金・単価設定: 上記課金項目それぞれに対し、テナントごと、または契約プランごとに0円以上の単価を設定できること。
- 適用期間: 各単価は「適用開始日」を持つ（2.4節の通り、常に月初から適用、当月中の日付は設定不可）。過去の単価も履歴として保持し、対象月の請求計算時にその月に有効だった単価を参照する。
- 管理UI: 上記を設定できる画面を `billing` 機能としてPF管理者画面にメニュー化する。

## 4. 端数処理・締め処理

### 4.1 端数処理・税計算
- 端数処理: 単価×利用量で生じた1円未満の端数は、明細行ごとに切り捨てる（合計金額算出時ではなく行ごとに処理し、後から合計する）。
- 消費税: 明細合計に対して税率（10%、標準税率）を乗じ、税額は1円未満を切り捨てる。

### 4.2 バッチ処理（締め処理）
- 実行タイミング: 前月分の統計情報について、締め切りルール（2.3節）に従った日時（例: 毎月X日0:00 JST）に集計・積算処理を実行する。
- 再集計機能: データ遅延等で再計算が必要になった場合の手動リカバリ機能を提供する。ただし、**確定済み（`finalized`）請求は直接書き換えない**（4.3節参照）。

### 4.3 請求ステータスとスナップショット保存

前回のブレストで追加提案し、採用が確定した項目:

- **請求ステータス:** 各月の請求は `draft`（計算中/未確定） → `finalized`（確定・請求書発行済み） → `corrected`（訂正後）のライフサイクルを持つ。`finalized`後に再集計が必要になった場合は、既存レコードを上書きせず**訂正差分（アジャストメント）として別レコードを追加**する。これにより「なぜ金額が変わったか」を後から追跡できる（会計上の要件）。
- **計算根拠のスナップショット保存:** 単価マスタは将来変更される可能性があるため、「その月の請求はどの単価・どの利用量で計算したか」を計算時点でスナップショットとして保存する。既存の`audit_logs`（操作ログ）とは別に、`billing_invoices`（請求書ヘッダ: テナントID、対象月、ステータス、合計金額等）と`billing_line_items`（明細行: 項目、利用量、単価、小計 — 計算時点の値をコピーして保持）の専用テーブルを新設する。

## 5. 未確定・次回検討事項

| 項目 | 内容 |
|---|---|
| 締め切り日数の具体値 | 「翌月X日X時」のXを運用開始前に確定する必要がある |
| 想定利用量閾値のデフォルト値 | ビルショック通知の「150%」等の具体的な数値・テナントごとのカスタマイズ可否 |
| 個別デバイス異常検知の実装方式 | リアルタイム監視 or 日次バッチ、判定ロジックの具体化 |
| 無制限テナントの請求処理 | 従量課金対象外とした場合の請求フロー（固定額行を明細に含めるか、billing対象外テナントとして完全に除外するか） |
| 消費税率の設定方法 | ハードコードか、税率マスタとして持つか（将来の税率変更に備える場合） |
